## Summary

Wye stops being a list of products kept in the app's data and becomes a window on **any folder you open** — a workspace. Inside it, every service folder can hold its own knowledge vault in `<folder>/.wye/`, created by running `wye init` in that folder (or right-click › Init Wye here in the app). Each vault is what a product is today, so everything Wye does per product works per service. The rail shows each vault as a root of Documents; Goals, Work, Inbox and Pinned show all reachable vaults together. A Files section lets you browse every file of the folder and open it in a tab with the VS Code editor. An agent that changes code in a folder writes what it learned back to that folder's vault. Later — designed, not built — a vault can link to a shared vault (company knowledge in its own git repo, cloned by you) and read it.

### How it works
1. In `services/payments` you run `wye init`: `services/payments/.wye/` appears with a first definition from the code, `_agent.md` and a CLAUDE.md pointer; the nearest parent vault gains a link to it, and it a link back.
2. In the app you open the monorepo folder (or any folder in it). Wye follows the links from the vaults it finds — no full scan each time — and shows each vault as a root in Documents.
3. Files lists the folder's files; a click opens one in a tab, read-only, in the VS Code editor; right-click on a folder without a vault offers Init Wye here.
4. A Claude Code session that edits `services/payments/src/…` reads `services/payments/.wye` first, and its decisions and tasks are proposed into that vault; the Inbox shows "payments" on each.

### Risks and constraints
- constraint:wf2.text-canonical — kept: the links and the vault are text in the folder's git; the registry entry `wye init` makes in the app's data is this machine's pointer only (decision:wf2.vault-first-slice) and goes when workspaces exist.
- constraint:wf2.one-defining-place — a vault's ids carry its slug; init refuses a slug its parent, siblings or children use. Two unrelated vaults on one machine can still share a slug: the app shows the second as `<slug>-2` until task:wf2.workspace-open.
- constraint:wf2.person-approves — init writes links in the parent and the children it takes over and names each file it changed; reading links never rewrites them.
- constraint:wf2.local-first, constraint:wf2.no-custom-pages, constraint:wf2.pr-is-the-persons — untouched by this slice.
- Risk — a vault made before a child vault describes the child's code as one of its modules; nothing removes those pages when the child is inited.
- Risk — agents outside Wye only follow AGENTS.md / CLAUDE.md, and the note names `--product <slug>`, which works only while the app has the vault open.
- Risk — `_sessions`, `_changes`, `_hooks`, `_impact` are gitignored in a vault, so a teammate's clone has the knowledge but not the pending change records.

### Contradictions
- decision:wf2.vault-keeps-folders against the choice of decision:wf2.vault-is-a-product-in-wye (flat `product.md` / `docs/` / `system/`): the person's answer overrules the layout sentence; the edit waits for approval (task:wye.edit-the-choice-of-decision-wf2).
- req:wf2.vault-init promises skills of its own; init writes none from the code — question:wf2.vault-service-skills is open, so the requirement is not marked shipped.
- question:wf2.workspace-root-vault and question:wf2.write-back-spanning-vaults are resolved by the two decisions above; question:wf2.cross-vault-ids stays open with its assumption.
- The verdicts recorded on decision:wf2.vault-is-a-product-in-wye against decision:wf2.product-model, decision:wf2.product-transfer and req:wf2.store.products are still listed there; with the layout kept and the registry entry as the bridge, this slice changes none of the three.
