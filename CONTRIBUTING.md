# Contributing to Wye

Thanks for looking. Wye is young and moves fast; the notes below are what you need to be useful in an afternoon.

## Where to talk

- **Ideas and questions** — [Discussions](https://github.com/emlab-ai/wye/discussions): *Ideas* for what Wye should
  do, *Q&A* when something is unclear, *Show and tell* for a product you described with it.
- **Bugs** — an [issue](https://github.com/emlab-ai/wye/issues) with what you did, what happened, and the
  `wye check` / test output when there is any. Issues labelled `good first issue` are bounded and have a pointer
  into the code.

## Run it

```bash
git clone https://github.com/emlab-ai/wye.git && cd wye
npm install
./install.sh                                  # `wye` on your PATH, the Claude Code skills in ~/.claude/skills
wye build --root data/products/wye && wye check --root data/products/wye
npm run dev                                   # http://localhost:3000 (…next dev -p 3456 for the port the CLI expects)
npm test                                      # node tests (parser, ontology, memory, impact, evals) + vitest for the web app
```

Node 18+. The agent features need `claude` (Claude Code) or `codex` on your PATH; everything else runs without them.

## How the repo is organised

- `lib/` — the graph core: `parse.js` (markdown → nodes and edges), `graph.js` (queries, packet, impact, lint),
  `judge.js` (model calls, cached), `init.js` (a definition from code).
- `bin/wye.js` — the CLI; `bin/wye-graph.js` the graph-only commands.
- `packages/web/` — the Next.js app (`src/lib` pure modules with vitest tests, `src/components`, `src/app`).
- `packages/desktop/` — the Electron shell.
- `schema/base-ontology.md` — the base types; `prompts/` — the agents' instructions (also the shipped skills);
  `templates/` — document skeletons.
- `data/products/wye/` — **Wye's own definition.** The app is described in itself: its requirements, decisions,
  rules, components and tests are documents here, and the graph built from them is what the tests and the agents
  read. `docs/type-system.md` explains the model.

## How changes happen here

Wye eats its own food. A change of behaviour starts as knowledge, not as code:

1. **Say what changes in the definition.** A new behaviour is a `req:` (when / then / unless) on the requirements
   page of its area (`data/products/wye/projects/v2/docs/requirements-*.md`); a choice among alternatives is a
   `decision:` on the Systems page of its area; a rule the code enforces is a `rule:` with a `source:`. Write them
   `status: proposed`. In the app this is a Prompt Request (⌘P); from a clone it is editing the markdown.
2. **Build it**, keeping the ids stable and the definition true: the cards that name files (`component:`, `lib:`,
   `op:`) are regenerated by `node scripts/cards.js --write`.
3. **`wye check --root data/products/wye`** must report 0 errors; `npm test` must pass.
4. **Commit to `main`** with a message that says what changed and why, in sentences — the log is part of the
   memory. While Wye is a prototype there are no feature branches (`constraint:wf2.main-branch`); for a pull
   request from a fork, one PR per change, rebased on `main`.

The rules every change respects are on the Constitution page of the app (`/wye/constitution`): text files in git are
canonical; every id is defined in exactly one place; knowledge is typed blocks, not prose or chat; agents write as
proposed and a person approves; nothing is a page of its own — every screen is a document made of existing blocks.

## Style

Match the file you are in. Comments say why and name the requirement or decision they serve (`rule:app-link`,
`decision:memory.bitemporal`) — that link is how the graph finds the code. Tests live next to the module they test
(`x.test.ts`) or under `test/` for the core. No new dependency without a sentence on why in the commit message.
